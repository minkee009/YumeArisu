### 1. 제어의 역전 (IoC)과 플랫폼 종속 기능 주입

플랫폼마다 근본적으로 작동 방식이 다른 영역들이 있습니다. 가장 대표적인 것이 파일 시스템(File I/O)과 입력 장치(Input)입니다.

데스크탑은 일반적인 디렉토리 경로에서 파일을 읽어오지만, 안드로이드는 APK 내부에 압축된 `AssetManager`를 통해 리소스를 읽어야 합니다. 이를 해결하기 위해 `Core`에서는 인터페이스만 정의하고, 실제 구현체는 각 플랫폼 프로젝트에서 주입하는 방식을 사용해야 합니다.

``` C#
// [YumeAris.Core]
public interface IFileSystem
{
    byte[] ReadAllBytes(string path);
}

// [YumeAris.Android]
public class AndroidFileSystem : IFileSystem
{
    public byte[] ReadAllBytes(string path)
    {
        // 안드로이드 AssetManager를 이용한 읽기 로직
    }
}
```

작성하셨던 `SystemBase`의 `StartUp(TConfig config)` 인자를 활용하여, 엔진 초기화 시점에 `AndroidFileSystem` 같은 플랫폼 전용 구현체를 `Core` 시스템으로 넘겨주는 방식이 유효할 것입니다.

### 2. OS 생명주기 (Lifecycle) 매핑

데스크탑 앱은 개발자가 직접 `while(true)` 형태의 렌더 루프를 통제하지만, 모바일 OS(Android, iOS)는 운영체제가 앱의 생명주기를 강제로 통제합니다.

사용자가 게임 중에 전화가 오거나 홈 화면으로 나가면 OS는 즉각적으로 앱을 일시 정지(Pause)시킵니다. 따라서 기존 `SystemBase`의 `StartUp`과 `ShutDown` 외에도, 모바일 환경에 대응하기 위해 시스템 전체를 멈추고 재개할 수 있는 `Suspend(OnPause)`와 `Resume(OnResume)` 같은 상태 전환 인터페이스가 코어 레벨에 추가로 필요해집니다. 이때 그래픽스 리소스(텍스처, 셰이더 등)가 유실되는 컨텍스트 로스트(Context Lost) 현상도 함께 처리해야 합니다.

### 플랫폼 서비스 주입 구조 예시

`Core` 레벨에서 플랫폼 추상화를 위한 서비스 인터페이스들을 묶어두고, 이를 각 시스템의 `TConfig`로 전달하는 형태가 될 것입니다.


``` C#
// [YumeAris.Core] 플랫폼이 제공해야 할 기능들의 명세
public interface IPlatformServices
{
    IFileSystem FileSystem { get; }
    IGraphicsContext GraphicsContext { get; }
    IWindowSystem Window { get; }
}

// [YumeAris.Core] 엔진의 핵심 생명주기를 관장하는 시스템
public class RenderSystem : SystemBase<RenderSystem, IPlatformServices>
{
    private IGraphicsContext _graphics;

    public override void StartUpInternal(IPlatformServices config)
    {
        // 플랫폼별로 다르게 구현된 그래픽스 컨텍스트를 주입받음
        _graphics = config.GraphicsContext;
        _graphics.Initialize();
    }

    public override void ShutDownInternal()
    {
        _graphics?.Dispose();
    }
}
```

이렇게 구성하면 `YumeAris.Desktop`에서는 GLFW/SDL 기반의 서비스 구현체를 넘겨주고, `YumeAris.Android`에서는 Android Native 기동에 맞는 구현체를 넘겨주기만 하면 되므로 `Core` 내부 로직은 단 한 줄도 수정할 필요가 없어집니다.

### 처음에 고민하셨던 ImGui 문제의 최종 해결책

이 규칙은 처음 질문하셨던 **ImGui 처리 위치**에 대한 고민도 완벽하게 해결해 줍니다.

ImGui 역시 플랫폼(OS 윈도우 핸들, 마우스/키보드 입력 이벤트 펌핑 방식)에 강하게 종속되는 렌더러와 백엔드를 가집니다. 따라서 이 구조를 적용하면 다음과 같은 아름다운 형태로 정리가 가능합니다.

1. **`YumeAris.Core`**: ImGui의 그리기 명령(`ImGui.Begin`, `Button` 등)과 디버그 UI를 등록받는 이벤트 버스만 가집니다. (플랫폼 독립적)
2. **`IPlatformServices` 인터페이스**: `RenderImGui()` 같은 추상화된 메서드나 ImGui 초기화 전용 인터페이스를 포함시킵니다.
3. **`YumeAris.Desktop`**: 데스크톱용 ImGui 컨트롤러(예: Silk.NET.ImGui 등)를 구현하여 코어에 주입합니다. 메인 루프에서 주입된 컨트롤러의 프레임을 넘겨주고 최종 렌더링을 수행합니다.
4. **모바일 빌드 (`Android`, `iOS`)**: 만약 모바일 환경에서 ImGui 디버그 창이 필요 없다면, `StartUp` 시점에 아무 동작도 하지 않는 Null Object(빈 구현체)를 주입하거나 릴리즈 빌드 조건부 컴파일(`#if DEBUG`)로 처리하여 컴파일 타임 및 런타임 오버헤드를 쉽게 지울 수 있습니다.
